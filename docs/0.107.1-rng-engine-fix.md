# v0.107.1 歪种根因与修复记录（RNG 引擎切换 + Neow 事件种子公式）

> 结论先行：游戏 v0.107.1 把全部种子随机流从 `System.Random` 换成了 **xoshiro256\*\***（`MegaRandom`），
> 且 Neow/古神事件的 RNG 种子必须是 `runSeed + 玩家槽位 + hash(事件Id)`。修复后对真实存档回放验证：**Neow 190/191（99.5%）**，4/4 今日手工种子逐位一致。

## 1. 根因

### 1.1 主因：PRNG 算法不匹配

从游戏自带的 `data_sts2_windows_x86_64/sts2.dll`（v0.107.1）反编译确认：

- `MegaCrit.Sts2.Core.Random.MegaRandom` = **xoshiro256\*\***（Redzen 移植，splitmix64 播种，
  `NextDouble = (NextULongInner() >> 11) * 2^-53`，`NextBool = Next(2) == 0`）。
- `Rng` 内部字段 `_random` 的类型是 `MegaRandom`，不再是 `System.Random`。
- 本项目 `SeedModel.Rng.GameRng` 此前一直用 `System.Random`（Knuth 减法滞后斐波那契）。

两套 PRNG 完全不同 → **所有**种子化随机流（`up_front`、事件 RNG、rewards、shops、遗物袋、遭遇、Boss、古神……）
逐位发散 → roll 出的种子与游戏对不上（歪种）。这不是数据问题，也不是个别 seed 问题，是引擎级差异。

### 1.2 次因：Neow 事件种子公式

游戏 `EventModel.BeginEvent`（v0.107.1）：

```csharp
Rng = new Rng((uint)((int)Owner.RunState.Rng.Seed
    + (IsShared ? 0 : Owner.RunState.GetPlayerSlotIndex(Owner))
    + StringHelper.GetDeterministicHashCode(Id.Entry)));
```

对 Neow（Id.Entry == "NEOW"，单人槽位 = 0）：

```
eventSeed = runSeed + 0 + hash("NEOW")
```

本项目旧逻辑是 `new GameRng(runSeed + PlayerNetId(=1))`（既少了 `hash("NEOW")`，又多加了个 1）。
`hash("NEOW") = 348630327` 其实代码里已经写了常量，但玩家偏移用的是 NetId 而不是槽位索引。

### 1.3 验证证据（真实游戏存档回放）

- 用户本地 Steam 云存档 `userdata/.../2868840/remote/profile1/saves/history/*.run` 记录了每一局的真实选项。
- 2026-08-22 当日手工测试的 4 个种子（L0H6CT7SA1 / W635Q4VTRS / XVE2D7FVKX / 9NN1U7D6NX），
  旧程序 0/4 命中，修复后 **4/4 逐项一致**（含两个正选项的展示顺序）。
- 全量 v0.107.1 历史（2026-06-19 ~ 2026-08-22，191 局到过 Neow）：**190/191 命中**。
  唯一未命中是 v0.107.1 发售首日（6/19）的存档，穷举 4×10^6 种“池子排除”组合也无法复现，
  疑似发售窗口热修/账号状态差异导致，当前账号状态下不可复现。

## 4. 已知残余问题（第二/三幕）

- **第二/三幕古神选项**：古神命中时选项集合正确（与官方 `BeginEvent` 种子公式 + 各古神池一致）。
- **第二/三幕古神身份**：July+ 成熟账号存档上身份命中率约 Act2 74% / Act3 65%；其余错位集中在
  v0.107.1 发售初期（6/19~6/30）存档，疑似 epoch 揭示进度（事件池/古神池随解锁变化）与发售热修窗口所致，
  而 roll 工具按“全解锁”假设模拟，无法感知历史解锁进度。
- **古神选项的条件分支**：官方若干古神（Orobas 的 `TouchOfOrobas/ArchaicTooth`、Pael、Tanx 等）在
  生成前会对“当前牌组/遗物状态”做 `SetupForPlayer` 判定；同一种子因到达时的牌组不同会得到不同选项，
  纯“只看种子”的开幕预览本质上是近似（`AncientEventLogic` 内已注释）。
  需要更高的精确度时必须接入牌组/遗物状态模拟（SeedRunEvaluator 的路线模拟），超出本次范围。

## 4b. NEOWS_BONES 奖励预览修复（2026-08-22 追加）

用户实测发现涅奥骨骰的奖励预览与游戏不一致，两处细节均为 #1 之外的独立缺陷，已修复：

1. **遗物池顺序**：`NeowRewardPreviewer.NeowsBonesRelicPool` 此前不是官方
   `Neow.AllPossibleOptions` 的枚举顺序（SilkenTress/MassiveScroll/ScrollBoxes/WingedBoots 位置错位），
   导致 `PlayerRng.Rewards.Shuffle` 的索引映射不同。已按官方顺序重排并验证。
2. **诅咒抽取位置**：游戏在领取奖励遗物**之后**才用 `RunRngSet.Niche` 抽诅咒，而新叶/万花筒的
   `AfterObtained` 会先消费 niche 流（新叶 1 次、万花筒 2×StableShuffle(4 池)=6 次）。工具的子预览
   恰好采用共享 `state.NicheRng` 先消耗、再抽诅咒的机制，池顺序修正后自动对齐。

验证：全部历史存档中 10 局选择过 NEOWS_BONES 的对局（含当日 DJWGBU0C5K），
“2 件随机涅奥遗物 + 诅咒”预览 **10/10 与游戏存档一致**。
例：DJWGBU0C5K 工具修正前=树叶药膏+精准剪刀+凡庸；修正后=树叶药膏+新叶+苦恼（WRITHE），与游戏完全一致。

## 5. 后续维护提醒

- 换引擎后 `GameRng.FastForward` 语义与官方 `Rng.FastForwardCounter` 对齐（每次推进一次原生抽取）。
- 游戏再有新版本时：先查 `sts2.dll` 中 `Rng._random` 字段类型是否仍是 `MegaRandom`，以及
  `EventModel.BeginEvent` 的种子公式是否变化；据此调整 `GameRng.ConfigureEngine` 的版本阈值。
- 曾计划基于 System.Random 复刻的 GPU 预筛方案（`src/SeedModel/Gpu/*`、`docs/gpu-*.md` 及对应测试）
  已随本次修复废弃删除——游戏引擎已是 xoshiro256**，该方案失去意义。若未来再做 GPU 加速，
  应直接移植 xoshiro256**（无分支纯整数运算，反而比 System.Random 更易上 GPU）。
- 会话内还做过一批临时验证脚本（`scratch/NeowSimProbe/`、`BatchValidate.ps1` 等，已被 .gitignore 忽略），
  如需复现“存档回放验证”，可直接在临时工作树或本地拷贝中重建。
